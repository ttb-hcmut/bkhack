During development, it's sometimes useful to perform direct data binding. No algebraization or typing of values. No responsibility designation or MVC separation. At least, not yet. Consider a problem where the service API needs to specialize for the front-end's (technical) use case, but the front-end is still too early in development for any use case to be known.

|                  | SQL | NoSQL (mongodb) | NoSQL (firestore) |
|------------------|-----|-----------------|-------------------|
| gateway api      | y   | y               | n[^ecto-firestore]|
| free sql         | y   | n               | n                 |
| api direct       | n   | n               | y                 |
| free sql direct  | n   | n               | n[^firesql]       |

[^ecto-firestore]: For Elixir, a firestore binding elixir-firestore exists. But our framework is not just vanilla Elixir, it is *Elixir Ecto*. All DBMS bindings should be uniformly Ecto.

[^firesql]: There's an NPM package FireSQL which we had hope would be to do this - translating SQL expression to Firestore commands or something like Firestore Structured Query. Unfortunately, the package seems to be outdated, evident by the fact that it was expecting an object-oriented API of firestore documents but today firestore documents API is function-based.
